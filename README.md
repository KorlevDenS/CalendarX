# Веб-сервис Calendar

Данный файл содержит обзор функционала и реализации тестового задания.
В нём описаны выбранные технологии, особенности реализации, основные
и дополнительные функции разработанного веб-сервиса. Основной акцент сделан
на описании причин принятия тех или иных решений при выполнении данного задания.

## Описание функционала

* Возвращает григорианский календарь согласно указанному пользователем году (цифра).
* Дополнительно реализована функция получения конкретного месяца конкретного года.
* Работает с годами от 1582 (дата введения григорианского календаря) по 9999 (ограничение введено с точки зрения смысла).
* Возвращает JSON тело с ошибкой при невалидных данных или возникновении какой-либо ошибки на сервере.
* Выходные дни помечаются флагом isWeekend для более удобной интерпретации возможным фронтендом.
* Также отдельный флаг показывает, является ли год високосным.
* Дни содержат название дня недели (не номер, так как например не везде понедельник это первый день недели).

## Архитектура

* Для приложения выбрана классическая архитектура MVC (Model View Controller).
[Model](src/main/java/korolev/dens/calendarx/model/domain) - объектное представление календаря, роль View ложится на
фронтенд (в данной реализации фронтенда нет, так что только JSON ответ). Controller - контроллер с REST методами.
* Приложение писалось как микросервис, предоставляющий календари.
* [Контроллер](src/main/java/korolev/dens/calendarx/controller/CalendarController.java) вызывает сервисы для выполнения
бизнес-логики и доступа к модели. Рядом с ним располагается
[CalendarXAdvice](src/main/java/korolev/dens/calendarx/controller/CalendarXAdvice.java) для представления обработки ошибок
как отдельного слоя и централизованной их обработки. Такой подход делать контроллеры чище и избавляет бизнес-логику от
большого количества блоков try-catch.
* [DTO](src/main/java/korolev/dens/calendarx/dto) - объекты обмена данными с клиентом и сериализации в JSON.
* [Шаблоны](src/main/java/korolev/dens/calendarx/model/template) используются хранения 14-ти уникальных вариантов
календаря без привязки к конкретному году.
* [Сервисы](src/main/java/korolev/dens/calendarx/service) реализуют основную бизнес-логику приложения.
Интерфейс [CalendarFactory](src/main/java/korolev/dens/calendarx/service/CalendarFactory.java) тут реализует шаблон
проектирования "Фабрика" (паттерн нужен для нескольких способов создания объекта, тут приведен для демонстрации).
[CalendarService](src/main/java/korolev/dens/calendarx/service/CalendarService.java) возможно
кажется избыточным, так как содержит просто вызов метода, но, как мне кажется, с точки зрения архитектуры он должен быть
для гипотетического расширения проекта.
* [Репозитории](src/main/java/korolev/dens/calendarx/service) предоставляют доступ к данным. В данном случае он один,
но к примеру, при добавлении базы данных, можно добавить в данный пакет JpaRepository или любой другой.

## Техническая реализация

* Приложение реализовано на Java 21 с использованием фреймворка Spring Boot 4.1.1.
* Приложение работает на сервере Tomcat.
* Для DTO и шаблонов календарей используются records, так как они идеально подходят для хранения read-only объектов.
* Валидация сделана при помощи аннотаций jakarta.validation. Также есть дополнительные созданные мной исключения.
При нормальной работе текущей версии и при условии отсутствии моих ошибок они не должны возникать, а существуют для
контроля валидности данных при гипотетическом расширении проекта.
* При помощи аннотаций Swagger описана схема DTO. Есть встроенный Swagger UI.
* Написаны [Unit-тесты](src/test/java/korolev/dens/calendarx) для [GregorianCalendarFactory](src/main/java/korolev/dens/calendarx/service/GregorianCalendarFactory.java),
  [CalendarMapper](src/main/java/korolev/dens/calendarx/mapper/CalendarMapper.java) и
  [CalendarXAdvice](src/main/java/korolev/dens/calendarx/controller/CalendarXAdvice.java). Тестами покрывался только
более-менее содержательный код.
* Для Unit-тестов использовался Jupiter JUnit 5 и Mockito.
* Настроен [простой CI](.github/workflows/ci.yml) через GitHub Actions. Запускаются тесты при push/pull request в
main (тут единственная ветка) и затем проверяется сборка если тесты прошли.
* Есть базовый мониторинг через Prometheus и Grafana с двумя дашбордами: [для JVM](grafana/provisioning/dashboards/jvm.json) и [для
Spring Boot](grafana/provisioning/dashboards/spring_boot.json). Дашборды взяты из открытой базы готовых дашбордов
и имеют лишь небольшие модификации от меня. Настроены с учетом возможного увеличения количества реплик.
* Настроен запуск и сборка приложения с помощью Docker и Docker Compose.

## Ключевые особенности

* Для григорианского календаря всего есть 14 уникальных годовых календарей, так как год может начинаться с одного из
7 дней недели, что даёт 7 вариантов, но при этом год может быть високосным (366 дней) и обычным (365 дней), значит число
вариантов умножается на 2.
* Приложение не генерирует каждый календарь с нуля, а использует 14 шаблонов из озу и формирует ответ на основе нужного.
* Коммуникация с клиентом согласно REST.
* Доступен мониторинг через Prometheus и Grafana.
* Unit тесты + GitHub CI.

## Рекомендации по запуску и использованию

* Основной способ запуска - через Docker Compose командой `docker compose up -d --build`. При таком запуске гарантировано
выполнение в изолированной среде и работа мониторинга.
* Все ссылки далее открываются локально после запуска приложения по проброшенным в [docker-compose.yaml](docker-compose.yaml) портам.
* Для проверки и просмотра OpenApi доступен Swagger UI по адресу `http://localhost:8088/swagger-ui/index.html`.
* Prometheus: `http://localhost:9090/targets`.
* Дашборды Grafana: `http://localhost:3000/dashboards`.
